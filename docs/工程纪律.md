# hutianSEOGEOAGent 工程纪律

> 来源：2026-08-08/09 安全线最终章收尾。从两个隐藏雷 + 一条防复活断言中提炼。
> 58/58 是"现在绿"；这三条纪律保证的是"将来的绿可信"。适用于后续所有线（业务腿同样适用）。

---

## 纪律一：修复必须被构建/产物验证

涉及生产产物（bundle、镜像、二进制）的修复，以 **build + grep 产物** 为判官，源码改了不算闭环。

- **活例**：P0-9（admin 登录页 token 提示）源码已改为 `import.meta.env.DEV` 条件显示，但 admin 缺 `vite-env.d.ts`，生产构建 tsc 直接报错出不了包——修复**从没进过生产 bundle**，长期停在假闭环。直到尾巴三要跑 `vite build` 做 bundle grep 才被挖出。
- **验收**：安全相关的前端修复，必须附 `build + grep 0 命中` 的产物级证据（命令输出记录进 review 报告），否则状态只能标"源码已改"，不能标"已闭环"。

## 纪律二：探针/门禁脚本自身也是被测对象

质量门自身的清理 / env / 进程管理是门禁的一部分；**门禁有 bug，所有"全绿"都不可信**。

- **活例**：verify.ps1 清理 glob `tenant-api*` 匹配不上 `go run` 子进程名 `hutian-tenant-api.exe`，残留旧进程污染下一轮回归；且探针 env 只设在冷启动路径，"服务已运行"分支探针拿不到密钥。已修为 WMI 父子 PID 清理 + env 前置。
- **验收**：探针/门禁脚本改动后，冷启动跑一遍、热启动（存在残留进程）跑一遍；回归结论前先确认"当前服务是哪个进程、跑的哪份代码"。

## 纪律三：安全删除必须带防复活断言

删除一个不安全面 = 删代码 + **加一条"它真的不在了"的回归断言**，防将来误加回来。

- **活例**：删除旧 `POST /api/v1/internal/token`（明文自报 header 签发端点）后，probe_cross_lang 断言⑥验旧端点 = 404——把"不存在"本身钉成回归，谁误加回来探针立刻红。
- **验收**：任何安全删除类提交，必须附对应红线断言；没有防复活断言的删除视为未完成。

## 盖章口径（防误读）

"安全线最终章"盖的是 **安全阻断项清零 + 四探针链守卫** 的章，**不是"生产就绪"** 的章。
含义：上线前必须零的阻断项，零了。不代表可以对外提供多租户服务。

阻塞"生产就绪"章的债（需排期）：

1. P0-10：admin token localStorage → httpOnly cookie（M5 同方案）
2. P0-1 收尾：`X-Internal-Secret` 服务密钥过渡态，待 /api/v1 剩余业务面迁 portal/admin 双轨后整组下线
3. P1-1：登录锁定（FailedLoginCount/LockedUntil 字段写入）
4. P1-9/10：cms 写工具纳入破坏性闸门 + cms_upload_media 路径白名单
5. P1-13/14：Schema 基线统一（SQL 文件为唯一基线）+ 软删唯一约束冲突
