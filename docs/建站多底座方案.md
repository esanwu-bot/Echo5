这个问题的本质，不是"加一个 WordPress 集成"，而是**把"建站底座"从一个硬编码的具体实现（siteBase）抽象成一个 CMS 适配器接口，让 siteBase 和 WordPress 成为这个接口的两个可插拔实现，按 workspace 选择用哪个**。你是 CRUD 老手，这就是经典的"端口与适配器"（接口 + 多实现 + 工厂按类型分发）——而且它是上一轮我们刚做的 MCP 实例池的**自然延伸**：上一轮是"同一种底座（siteBase）的不同实例按 url 路由"，这一轮是"不同种底座（siteBase vs WordPress）的不同实例按类型路由"。这个抽象做对了，将来接第三个底座（Ghost、Strapi、客户自建的 Node CMS）就是再加一个适配器，主干一行不动。

先看清 siteBase 现在在系统里的两个接触面，因为接 WordPress 这两面都要适配：

- **写入面**：MCP 工具（`cms_create_page`/`cms_configure_product`）→ siteBase admin API（`sitebase_client.py` 从 env 读 url）
- **读取面**：渲染器 `reader.ts` → siteBase public API（`getArticle`/`getProduct` 取数渲染）

WordPress 这两面的 API 形状、字段、鉴权全都不同（WP REST API `/wp-json/wp/v2/posts`、post/ACF/WooCommerce 数据模型、Application Password 鉴权）。所以适配也要分这两面做。下面按层给架构，再给你三个必须拍的决策点，最后给渐进路径。

## 分层架构

**第 1 层 · CMS 适配器接口（核心抽象，底座无关）。** 把壶天建站工具需要的能力抽成一个接口，跟具体底座解耦。伪代码给你看形状：

```
interface CmsAdapter {
  createPage(title, content, meta)      → pageId
  configureProduct(...)                 → productId
  getPage(id) / getProduct(id)          → 壶天 Article/Product 模型   // 读取面，给渲染器
  listPages() / listProducts()
  writeStructuredData(id, jsonld)       // SEO 写入
  submitSitemap(urls)                   // 收录提交
}
SitebaseAdapter implements CmsAdapter   // 现有 sitebase_client 的逻辑搬进来
WordpressAdapter implements CmsAdapter  // 新建，调 WP REST API + 字段映射
```

MCP 工具不再直接调 `sitebase_client`，而是调"当前 workspace 的 CMS 适配器"，适配器按 `cms_type` 分发。**关键纪律：siteBase 特有的字段假设要全部隔离进 `SitebaseAdapter`，接口本身底座无关**——否则 WordPress 适配器会被 siteBase 的字段形状绑架，"抽象"只是名义上的。这跟我们这程"复用资产不复用耦合"一脉。

**第 2 层 · 实例路由（按 workspace 选底座）。** `sitebase_instances` 表升级成 `cms_instances`，加 `cms_type`：

```
cms_instances: id, workspace_id, cms_type('sitebase'|'wordpress'),
               connection_config(json), status, health
  sitebase  → connection_config: { admin_url }
  wordpress → connection_config: { wp_url, auth: application_password/jwt }  // 加密存，NFR-T02
```

ADR 内部 token 的 payload 里，`sitebase_base_url` 升级成 `cms_instance`（`cms_type` + `instance_id` 或连接配置引用）。bridge 的 MCP 实例池从"按 `sitebase_base_url` 分实例"升级成"按 `cms_instance`（type + config）分实例"——上一轮的池子逻辑直接复用，key 从 url 换成 instance。

**第 3 层 · 写入面（MCP 工具 → 适配器分发）。** 两个方案：
- **方案 A**：`hutian_seo_mcp` 内部加 `wp_client.py`（跟 `sitebase_client.py` 并列），`cms_tools.py` 的工具函数按当前实例 `cms_type` 选 client。**工具 schema 不变、LLM 完全不感知底座差异。**
- **方案 B**：WordPress 用独立 MCP server，bridge 按 `cms_type` 路由到不同 MCP server。隔离更彻底，但多一套进程/依赖。

**第 4 层 · 读取面（渲染器）。** `reader.ts` 适配器化：`getArticle(id)` 按 workspace 的 `cms_type` 分发到 siteBase reader 或 WordPress reader（WP post → 壶天 Article 模型）。**但这里有个产品决策**（下面决策 1）：渲染层是壶天统一渲染，还是 WordPress 自己渲染。

**第 5 层 · 字段映射（最脏的活，单独设计单独测）。** siteBase 的 `sk_article/sk_product` 字段 ↔ WordPress 的 `post_title/post_content/ACF/WooCommerce` 字段。三个硬骨头：① **content 格式**——siteBase 可能存 markdown，WP 存 HTML/Gutenberg block，转换有损；② **结构化数据**——siteBase 的 JSON-LD 是壶天注入的，WP 通常靠 Yoast/RankMath 插件或自定义 meta，映射方式不同；③ **product**——WP 原生没有 product，要靠 WooCommerce 或 ACF custom post type。这层是接 WordPress 的主要工作量，别低估。

**第 6 层 · 鉴权。** WP 用 Application Password（Basic Auth）或 JWT 插件，跟 siteBase 的 admin JWT 不同。`cms_instances.connection_config` 加密存 WP 凭证，复用 `tenant_credentials` 那套 envelope 加密。

**第 7 层 · SEO/GEO 工具链的底座无关性（这个区分很重要）。** `run_diagnosis`/`check_schema` 读/`trace_citations` 是**底座无关**的——它们 curl 抓渲染出来的 HTML、解析 JSON-LD、算评分，不关心背后是 siteBase 还是 WP。但 `check_schema` 写/`submit_sitemap` 是**底座相关**的——写结构化数据要适配（写 siteBase meta vs 写 WP meta/插件）。所以"审计/诊断"不用适配，"写入/提交"要适配。

## 三个你必须拍的决策点

| 决策 | 选项 | 我的倾向 + 理由 |
|---|---|---|
| **1. 渲染层** | (a) 壶天统一渲染，WP 只当内容存储 / (b) WP 自己渲染，壶天只写内容+审计 | 取决于产品定位。若壶天卖"SEO/品牌/JSON-LD 物理保证"→ (a)，保持 γ 渲染器的核心价值，但要做 WP 读取面适配；若客户是"已有 WP 站、壶天帮做 SEO"→ (b)，简单但壶天失去渲染控制（WP 主题 SEO 参差、品牌单源难保）。**这个决定适配器的读取面做不做，是最大的分叉** |
| **2. MCP 组织** | (a) `hutian_seo_mcp` 加 `wp_client`，工具 schema 不变 / (b) 独立 WP MCP server | (a) 起步——LLM 无感、工具 schema 统一、改动小；WP 适配重了（Gutenberg/ACF 复杂）再演进到 (b) |
| **3. WP 的 product 怎么存** | (a) WooCommerce product / (b) ACF custom post type | 取决于客户 WP 站是否已装 WooCommerce。装了→ (a)（电商语义全）；没装、只是内容站→ (b) 轻 |

## 渐进路径（MVP，别一上来全做）

1. **先抽象、不改行为**：把现有 `sitebase_client.py` 重构成 `SitebaseAdapter`，定义 `CmsAdapter` 接口，`sitebase_instances` → `cms_instances` 加 `cms_type`（现有实例全标 `sitebase`）。这一步零行为变化，纯重构，但把抽象层立起来——**先有接口，再谈第二个实现**。
2. **再实现 WordPress 写入面**：`WordpressAdapter.createPage` → WP post，先打通"一句话建页到 WP"。读取面按决策 1 做不做。
3. **然后字段映射 + 鉴权 + SEO 写入适配**：最脏的活放后面，单独测。

## 一条这程特有的纪律，接 WP 时务必守

**假成功要自报家门，在适配器层同样适用。** WordPress 适配器某个能力不支持（WP 没 siteBase 的某字段、WP API 限流、鉴权失败），要明确报错/降级，**绝不能静默返回假 page id 说"建好了"**——跟前面 siteBase public API 500 不 mock、取数容错三态是同脉。`cms_create_page` 到 WP 失败就报错，别返回假 id 让渲染器渲染一个不存在的页。

诚实边界：我没读 `sitebase_client.py`/`cms_tools.py`/`reader.ts` 的完整实码（据 trace + 这程记忆推断），所以适配器接口的具体签名、字段映射的具体字段、WP API 的具体端点和版本兼容，以实码和 WP 版本文档为准；但"适配器抽象 + 按 workspace 路由 + 字段映射是最脏的活 + SEO 读工具底座无关/写工具底座相关 + 假成功不静默"这些是架构判断，不依赖实码，我有把握。

收口一句：接 WordPress 的正确姿势不是"在 siteBase 旁边再写一套 WordPress 调用"，而是**先把"建站底座"抽象成 CMS 适配器接口，让 siteBase 和 WordPress 都成为它的实现，按 workspace 的 `cms_type` 路由**——这是上一轮 MCP 实例池"按 url 分实例"到"按底座类型分实例"的自然延伸，抽象做对了，接第三个底座就是再加一个适配器。真正的活不在"调 WP API"，在第 5 层字段映射（content 格式转换、结构化数据落点、product 用 WooCommerce 还是 ACF）和第 1 层那个产品决策（壶天统一渲染还是 WP 自渲染）——后者决定适配器的读取面做不做，是最大的分叉，建议你先拍。这三个决策点你拍了，我可以帮你把这个架构落成一份 ADR（CMS 适配器抽象，接 ADR-cross-lang 的体例）+ 技术方案 + 渐进任务清单，跟多租户那套文档串成链。要不要我现在就起这份 ADR 草稿，还是你先拍三个决策、我按你拍的落？球在你，我待命。

## 核心设计（七层）

### 第 1 层 · CmsAdapter 接口（底座无关）

```python
class CmsAdapter:
    # 写入面（MCP 工具调）
    def create_page(self, input: PageInput) -> {id, url}
    def configure_product(self, input: ProductInput) -> {id, url}
    def write_structured_data(self, id, jsonld) -> None
    def submit_sitemap(self, urls) -> SubmitResult
    # 读取面（γ 渲染器调）
    def get_page(self, id) -> Article      # 返回 canonical Article
    def get_product(self, id) -> Product   # 返回 canonical Product
    def list_pages(self) / list_products(self)
```

- `SitebaseAdapter`：现有 `sitebase_client.py` 逻辑搬入，siteBase 特有字段假设**全部隔离在此**
- `WordpressAdapter`：新建 `wp_client.py`，调 WP REST API + WooCommerce REST API
- **纪律**：接口底座无关，siteBase/WP 特有假设隔离进各自适配器，否则 WordPress 适配器会被 siteBase 字段形状绑架，"抽象"只是名义上的

### 第 2 层 · 实例路由（按 workspace 选底座）

`sitebase_instances` → `cms_instances`，加 `cms_type`：

```
cms_instances: id, workspace_id, cms_type('sitebase'|'wordpress'),
               connection_config(json, 加密), status, health
  sitebase  → connection_config: { admin_url }
  wordpress → connection_config: { wp_url, woo_consumer_key, woo_consumer_secret }  # 加密存，NFR-T02
```

- `ADR-cross-lang` 内部 token payload：`sitebase_base_url` → `cms_instance`（`cms_type` + `instance_id` + connection 引用）
- bridge MCP 实例池（`pool.ts`）：key 从 `sitebase_base_url` 升级到 `cms_instance`（type + config），**复用上一轮池子逻辑**，只是 key 维度变了

### 第 3 层 · 写入面（MCP 工具 → 适配器分发，决策 2）

- `hutian_seo_mcp` 加 `wp_client.py`（跟 `sitebase_client.py` 并列）
- `cms_tools.py` 工具函数按当前实例 `cms_type` 选 client（`sitebase_client` 或 `wp_client`）
- **工具 schema 不变**（`cms_create_page` 等入参不变），LLM 无感
- 适配器内部做 canonical → 底座字段映射（第 5 层）

### 第 4 层 · 读取面（γ 渲染器统一渲染，决策 1）

- `reader.ts` 适配器化：`getArticle`/`getProduct` 按 workspace `cms_type` 分发
  - sitebase → 现有 siteBase public API
  - wordpress → WP REST API（`/wp-json/wp/v2/posts/{id}`）+ WooCommerce（`/wp-json/wc/v3/products/{id}`）→ 映射到 canonical `Article`/`Product`
- **γ 渲染器本身不变**（只认 canonical），变的是 reader 取数来源
- 保持：SEO 物理保证（head+JSON-LD 在初始 HTML）、品牌单源（brand 从 `workspace.brand_name` 派生，**不读 WP 的 site title**）、JSON-LD 注入（`schema-mapping.ts` 不变）

### 第 5 层 · 字段映射（canonical ↔ 底座，最脏的活，单独设计单独测）

canonical 模型（壶天定义，底座无关）：

| canonical | siteBase 映射 | WordPress 映射 |
|---|---|---|
| Article.title | sk_article.title | post_title |
| Article.content | sk_article.content（markdown）| post_content（**markdown → HTML/Gutenberg**，有损转换）|
| Article.meta/jsonld | sk_article.meta | WP post meta（或 Yoast/RankMath 字段，若客户装了）|
| Product.name/sku/price | sk_product.* | WooCommerce product name/sku/regular_price |
| Product.image | sk_product.image | WP 媒体库（`/wp-json/wp/v2/media` 上传）或外链 |
| Product.specs | sk_product.specs | WooCommerce attributes / meta |

三个硬骨头：① **content 格式**——canonical 建议存 markdown，写 WP 转 HTML、读 WP 转回（有损，需约定）；② **结构化数据落点**——WP 写 post meta 还是 SEO 插件字段（见开放问题）；③ **product 依赖 WooCommerce**（决策 3 前提）。

### 第 6 层 · 鉴权

| 底座 | 鉴权方式 | 存储 |
|---|---|---|
| siteBase | admin JWT（现有）| 现有 |
| WordPress | Application Password（WP 5.6+ 内置，Basic Auth）或 JWT 插件 | `cms_instances.connection_config` 加密 |
| WooCommerce | consumer key/secret（OAuth 1.0a 或 query string）| 同上 |

适配器内部处理各自鉴权，接口层不暴露鉴权细节；凭证加密复用 `tenant_credentials` 的 envelope 加密（NFR-T02）。

### 第 7 层 · SEO/GEO 工具链的底座无关/相关

| 工具 | 底座相关？ | 说明 |
|---|---|---|
| run_diagnosis / check_schema 读 / trace_citations | **无关，不用适配** | curl 抓渲染 HTML、解析 JSON-LD、算评分，不关心底座 |
| check_schema 写 / submit_sitemap | **相关，要适配** | 写结构化数据/提交收录按底座适配（走适配器 `write_structured_data`/`submit_sitemap`）|

**简化点**：因决策 1 渲染层统一，γ 渲染器注入的 JSON-LD 是壶天控制的，`check_schema` 读到的 JSON-LD 对 siteBase 和 WP workspace **一致**（都是 γ 注入的）——读取面 SEO 工具天然底座无关。

## 纪律保障（这程纪律在适配器层的落地）

- **单一抽象、可插拔实现**：`CmsAdapter` 底座无关，siteBase 特有假设全隔离进 `SitebaseAdapter`
- **复用资产不复用耦合**：γ 渲染器/schema-mapping/SEO 读工具复用，底座耦合隔离进适配器
- **假成功要自报家门**：WP 适配器能力不支持/API 限流/鉴权失败 → **明确报错，绝不静默返回假 id/假数据**（跟 siteBase public API 500 不 mock、取数容错三态同脉）；`cms_create_page` 到 WP 失败就报错，别返回假 id 让渲染器渲染不存在的页
- **品牌单源**：WP workspace 渲染品牌仍从 `workspace.brand_name` 派生，不读 WP site title（PRD §4.1）
- **多租户隔离**：WP 实例路由仍走 `ADR-cross-lang` 签名 token + MCP 实例池，`cms_instances` 按 workspace 隔离；WP 凭证按 tenant 加密隔离

## 开放问题

- **WP 版本/插件兼容**：WP REST API 在不同 WP 版本/插件配置下行为差异；WooCommerce REST API 需 WooCommerce 已装。决策 3 用 WooCommerce product，**客户 WP 站没装 WooCommerce 怎么办**——MVP 提示装 WooCommerce（不降级 ACF，守住决策 3），v2 再评估 ACF 兜底
- **content 格式有损转换**：markdown ↔ HTML/Gutenberg 转换丢格式，需约定 canonical content 格式（建议 canonical 存 markdown）
- **结构化数据落点冲突**：WP 的结构化数据写 post meta / Yoast / RankMath / 自定义字段；若客户已装 SEO 插件，壶天注入的 JSON-LD 跟插件可能冲突——需约定壶天写哪、是否检测插件
- **WP 媒体库**：image 上传到 WP 媒体库 vs 外链，canonical Product.image 处理策略
- **同步方向**：MVP **单向写**（壶天 → WP），WP 后台手动改了内容壶天不感知；双向同步留 v2
- **密钥/凭证轮换**：WP Application Password / Woo consumer secret 轮换机制，复用 `tenant_credentials` 的 key_version
