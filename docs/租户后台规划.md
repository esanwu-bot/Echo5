## 0. 命门：租户后台 ≠ ops 后台（信任模型相反，先划清再写一行代码）

| 维度 | ops admin（已建，超管面） | tenant self-service（本文，租户面） |
|---|---|---|
| 登录主体 | 平台超管 super-admin | 租户成员 owner/admin/member |
| 数据视野 | 全平台所有租户 | **仅自己 `tenant_id` 下** |
| 隔离护栏 | 超管强鉴权 + 全操作审计 + IP/2FA；**不挂** tenant_id 隔离中间件（挂了做不出总览） | 租户 JWT + **强制** tenant_id 隔离中间件 `where tenant_id=ctx.tenant` |
| 调 tenant-api 哪组接口 | ops 管理接口族（超管鉴权中间件） | **tenant 自服务接口族**（租户鉴权中间件，强制注入 ctx.tenant） |
| 典型视图 | 租户列表 / 全局配额 / 全平台审计 | 我的总览 / 我的工作空间 / 我的席位 / 我的订阅 / 我的凭证 / 我的审计 |
| 最怕什么 | 超管口裸奔 = 全平台泄露 | 串数据 = 看见别租户 |

> 这张表是本文脊柱。Trae 照它，就不会把超管护栏搬到租户面（租户面做不出"只看自己"），也不会把租户隔离搬到 ops 面。**两套鉴权中间件、两组接口族，物理分开。**

## 0.1 两条调用链（别把所有租户请求都绕去签内部 token）

ADR 的 HMAC 内部 token 是给"调 siteBase 业务工具"用的（bridge/MCP 路由 siteBase 实例才需要 `sitebase_base_url`）。租户后台有两条性质不同的链，分清免得过度设计：

| 链 | 何时走 | 路径 | 用不用 ADR 内部 token |
|---|---|---|---|
| **链① 元数据自服务** | 租户看/改自己的 workspaces/seats/subscriptions/usage/audit | 租户 JWT → tenant-api 租户鉴权中间件 → 注入 ctx.tenant → 直查 hutian `where tenant_id` → 返回 | **不用**，tenant-api 自己查自己库 |
| **链② 触发 Agent 工具** | 租户在自己的后台/工作台点"为这个 workspace 跑诊断/建一页" | 租户 JWT → tenant-api 验 → 签 ADR 内部 token → BFF/工作台透传 `X-Tenant-Token` → bridge/MCP 验签 → 按 `sitebase_base_url` 路由 siteBase | **用**，走 ADR |

读法：租户后台 90% 的请求是链①（读自己的元数据），只有"触发干活"才走链②。文档/实现别把链①也绕去签内部 token。

## 0.2 三表面架构决策（ops 独立 / portal 并入 web）

| 表面 | 归属 app | UI 栈 | 理由 |
|---|---|---|---|
| marketing + workbench + **portal（租户自服务）** | `apps/web`，portal 用 `(portal)` Route Group | **轻量栈**（Tailwind 自实现，**不引 antd**） | 租户登录后"干活"与"管账号"是连续体验，同 app 共享租户会话、不跨域丢会话；用轻栈不污染客户站 bundle |
| ops admin | `apps/admin`（独立） | antd | 超管口不能与客户站同构建同域；antd 重依赖只留在独立 app |

> 与上轮给 ops 的"独立 app"倾向是**对照**：ops 独立、portal 并入。portal 若也用 antd，antd 就进 apps/web，破 PRD §8/技术方案"客户站刻意不引重依赖"。所以 **portal 表格/表单用 web 已有轻量组件**，不引 antd。以 monorepo 现状/部署约束为准，最终你/Trae 看实际结构定，但倾向如上。

## §1 租户自服务后台 PRD

### 1.1 一句话定位

租户成员登录壶天后，在 portal 里管**自己租户**的品牌/工作空间、成员席位、订阅用量、siteBase 凭证、操作审计——所有数据严格限定在自己的 `tenant_id` 内，是"租户自己服务自己"的面，与超管 ops 面互补。

### 1.2 视图清单（7 视图，对应表读取关系）

| 视图 | 读/写 | 主要表 | 关键能力 | 红线 |
|---|---|---|---|---|
| 我的总览 | 读 | subscriptions + usage_meters + plan_quotas + workspaces（聚合，仅本 tenant） | 用量进度条、配额、订阅状态、到期/试用倒计时、工作空间数 | 聚合查询强制 `tenant_id` |
| 工作空间·品牌 | 读/写 | workspaces（仅本 tenant） | 列表/新建/归档 workspace；改 `brand_name`/`industry`/`fallback_copy_json`（**brand 单源第三段=租户在此填品牌**） | 改 brand 触发渲染器兜底重算；归档不删 siteBase 实例 |
| 席位·成员 | 读/写 | seats + users（仅本 tenant） | 邀请/移除成员、分角色、看席位占用 vs `seats_limit` | 超 `seats_limit` 拒绝并提示升级；owner 不可移除自己 |
| 订阅·计费 | 读/（升级占位） | subscriptions + usage_meters + invoices（可选） | 当前 plan、用量明细、到期、试用、账单历史、升级入口 | **MVP 升级=占位/联系**，不接支付网关（trace §0.8 支付未集成） |
| 凭证 | 读元信息/轮换/吊销 | tenant_credentials（仅本 tenant 的 workspace） | 看 workspace 凭证状态/`last_rotated_at`/`key_version`；触发轮换/吊销 | **绝不渲染明文 secret**（NFR-T02，同 ops 凭证红线） |
| 审计 | 读 | audit_logs（仅本 tenant） | 本租户操作流水，区分 human/agent，按 workspace/时间筛 | 只读，不可删 |
| 个人·安全 | 读/写 | users（仅自己行） | 改密码、启停 2FA（TOTP）、看登录设备/最近登录 | 2FA secret 加密存，备份码一次性 |

### 1.3 功能需求（FR-TS）

| ID | 需求 | 用户故事 | 验收 |
|---|---|---|---|
| FR-TS01 | 租户登录 | 作为租户成员，我用邮箱+密码（+2FA）登录 portal | 登录发租户 JWT；错密码/停用账号/2FA 错均明确拒绝 |

| FR-TS03 | 工作空间品牌自填 | 作为租户 owner，我填自己品牌名/行业/兜底文案 | 写入 workspaces.brand_name 等；渲染器/兜底 settings 读此值（闭合 brand 单源第三段） |
| FR-TS04 | 席位自管 | 作为 owner/admin，我加删成员、分角色 | 角色 owner/admin/member；超 seats_limit 拒绝；owner 自保护 |

| FR-TS09 | 触发干活走 ADR | 作为租户，我在 portal/工作台触发建站/SEO 工具 | 走链②：签 ADR 内部 token 透传 bridge/MCP，按 workspace 路由 siteBase |

| ID | 维度 | 要求 |
|---|---|---|

### 1.5 验收（租户后台 DoD）

- [ ] 租户 A 登录，7 视图只见 A 的数据；构造 A 的 token 取 B 的 workspace/席位/审计 = 404/空（不泄漏存在性）

- [ ] 工作空间改 brand_name 后，渲染器兜底品牌随之变（brand 单源第三段闭合）
- [ ] 超 seats_limit 加成员被拒；owner 不能移除自己
- [ ] 升级入口为占位/联系，**无真实支付调用**（MVP）
- [ ] 登录错密码/停用/2FA 错均明确拒绝，登录按 IP 限流
- [ ] `probe:tenant-selfservice` 绿（见 §3 门禁）

### 1.6 开放问题

- 登录用无状态 JWT + Redis 黑名单，还是 refresh token 表？倾向无状态 + 黑名单（trace §6 siteBase 同模式，Redis 已就绪），表方案留备选。

- portal 与 workbench 是否同登录态同 app？倾向同 apps/web 同租户会话（§0.2），最终看部署约束。

### 2.4 决策点（标清，别在 M7 拍死）

- **DP-1 workspace 级成员授权**：MVP **不建** `workspace_members` 表，seats 保持 tenant 级（成员看本 tenant 全部 workspace）。v2 若需"成员 A 只管 workspace X"，再建 `workspace_members(workspace_id, user_id, role)`。**别在 seats 加 workspace 字段**搞乱 tenant 级语义。

### 2.5 索引/约束要点

- `users.email` unique；`seats(tenant_id, user_id)` 联合唯一（已有）回填后仍成立。
- `login_audit(user_id, created_at)` 复合索引；`invoices(tenant_id, period_start)` 复合索引。
- 所有租户后台查询走 `tenant_id` 前缀（ORM 基类强制，复用 M6）。
