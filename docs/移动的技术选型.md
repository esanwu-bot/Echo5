先定一个前提，否则原型和选型都会跑偏：**移动端 workbench 不是"把桌面三栏塞进 375px"**——那是反模式。桌面那套左栏会话+中栏对话+右栏四标签+底栏，在手机上必须做信息架构重构：中栏对话流是唯一主舞台，左栏会话降级成侧滑抽屉，右栏 Diff/终端/产物降级成"对话流里内联卡片+点击弹底部 sheet"，底栏时钟/分支信息收进顶栏或"我的"。下面原型就是按这个重构画的，不是缩小版桌面。

而选型那问，我得先破你的二选一前提——**uniapp 和 vue3 native 都建立在"用 Vue 把 workbench 重写一遍"上**，但壶天 apps/web 是 React 19，桌面 Wails 已经用 Vite alias 零复制复用了这套 React 组件。所以真正的第一个决策不是"uniapp 还是 vue native"，而是"能不能接受复用 React 组件的路线（RN/Capacitor）"，以及"要不要顺带出微信小程序"。这两刀切完，答案才出来。我在分析里画清楚，不替你在我没权拍的产品决策上骑墙，但给倾向。

## 技术选型分析：先破前提，再给倾向

### 你问的两个选项，共享一个该被质疑的前提

uniapp 和"vue3 native"**都是 Vue 生态**。选其中任何一个，意味着把 apps/web 那套 React 19 的 workbench 组件——`ChatStream / ToolCall / PlanChecklist / StatTiles / streamReducer / useAgentSession / markdown`——**用 Vue 重写一遍**。这直接违反这程守了全程的铁律：PRD §16.2 桌面版"共享 100% 前端代码"，技术方案 §17.2 桌面 Wails 已经用 Vite alias **零复制**复用了 apps/web 的 React 组件。如果移动端走 Vue，就是给 workbench 养**第三个前端**（web 一份 React、桌面复用、移动一份 Vue），回到"每个表面各写一套"的老路——而这正是我们前面 brand 单源、假数据保护那些坑的根因之一：多份实现必然漂移。

所以真正的决策树第一刀，不是 uniapp vs vue native，而是这两问：

```
                     要不要顺带出微信小程序？
                    /                      \
                  要                        不要
                  |                          |
        第二刀：能否接受                第二刀：能否接受
        "Vue 重写组件"换三端？          "复用 React 组件"路线？
          /        \                    /              \
        能          不能             能(套壳/RN)      不能(必须真原生且不要小程序)
        |            |                |                  |
     uniapp      重新评估         Capacitor套web      Expo/RN 真原生
   (一套出        小程序权重      或 Expo/RN          (维护 React 移动组件)
   app+小程序+H5) 是否真的高       复用率最高,
                                  与桌面Wails同脉
```

### uniapp vs "vue3 native" 的诚实对比（在你给的框内）

| 维度 | uniapp | "vue3 native"（vue 系原生方案） |
|---|---|---|
| 出端 | H5 + 微信/支付宝/抖音小程序 + App，**一套代码** | 通常仅 App（+H5），**出不了小程序** |
| 成熟度 | vue 系跨端最成熟，国内生态/坑文档齐全 | 生态明显弱于 uniapp，纯 vue 做真原生的主流就是 uniapp 或 capacitor 套 vue |
| 渲染 | App 端 vue→原生组件映射（nvue 原生渲染 / vue 页 webview 渲染混合） | 取决于具体框架，多数仍是 webview 或桥接 |
| 复用 apps/web React 组件 | **不能**，需 Vue 重写 | **不能**，需 Vue 重写 |
| 后台 SSE | 受限（小程序后台断网、App 后台被杀，需前台 SSE+推送补） | 同样受限 |
| 出海分发 | App 端正常；小程序在海外渗透低 | App 端正常 |

读法：**在 vue 系内部，uniapp 几乎严格优于"vue3 native"**——多小程序能力、更成熟、没有明显短板。所以"二选一我选 uniapp"。但这一行的前提是"已经决定用 Vue 重写"，而这个前提本身我下面要挑战。

### 我的倾向（带条件，不骑墙）

**默认倾向：不要选 vue 系任何一个，选"复用 React"路线。** 理由三条叠在一起：① 壶天已有 React web + Wails 零复制复用的现成范式，移动端套同一套是架构自洽的延续，不是新开一条线；② 目标画像是出海独立站客户（PRD §3 + 三轮车出海那程），微信小程序权重低，uniapp 的杀手锏（小程序）在这个画像下价值打折；③ workbench 是重 web 交互（SSE 流+markdown+工具块），WebView 壳的原生体验上限够用，跟桌面 Wails 同思路。

复用 React 路线内部再分两档：**Capacitor 套 apps/web 的 workbench 路由**（复用率≈100%，最快，代价是 WebView 性能/原生手势不如真原生）或 **Expo/React Native**（要真原生性能/原生导航时，维护一套 React 移动组件，streamReducer 这类纯函数逻辑层可直接跨端复用，UI 层重写）。鉴于 workbench 桌面版已经是 WebView 壳（Wails）且体验可接受，**我先推 Capacitor 套壳**，等真撞到 WebView 性能墙再上 Expo。

**uniapp 只在一种情况下上：产品决策确认"移动端必须同时出微信小程序"**（比如国内运营/演示/获客强依赖小程序）。那时"Vue 重写一次换 app+小程序+H5 三端"的账才可能赢过"RN 写 app + 另写小程序"。这是产品决策，我标成开放问题，不替你拍。

**"vue3 native"我没有推荐场景**——在我能合理理解的范围内（vue 系原生 app 方案），它相对 uniapp 没有更优的明确理由，反而丢小程序和成熟度。除非你指的"vue3 native"是某个我没对齐的具体框架，那结论可能变，见诚实边界。

### 一个跟选型无关、但移动端 workbench 必须设计的坑：后台 SSE

这条单列，因为它常被当成"选型决定因素"，其实不是——**所有方案在移动端后台 SSE 上都半残**：iOS 后台几秒杀网络、Android 厂商 ROM 杀后台、小程序后台断网、Capacitor/WebView 后台 EventSource 行为不一。所以解法不靠选框架，靠设计：**把 PRD §9 的"心跳+重连+Last-Event-ID 续传"从 web 的降级路径，升成移动端的主路径**（切后台流断=预期，回来续传，不假装不断）；关键完成结果用推送补（v2，APNs/FCM/个推）。这一点写进移动端 workbench 的通用约束，不影响上面选型结论。

### 给 Trae / 你的落地建议

- 先拍两个产品决策：**① 要不要微信小程序；② 能否接受 WebView 壳的原生体验上限**。这两问答完，选型自动出来（要小程序→uniapp；都不要→Capacitor 套 web；要真原生不要小程序→Expo）。
- 若走 Capacitor/Expo：先评估 apps/web 的 `useAgentSession` / SSE 逻辑对 Next.js/浏览器 API 的耦合度，确认套壳/搬移时要改几处——这是"复用率 100%"能否成立的判官。
- 若走 uniapp：接受 workbench 组件 Vue 重写，但**把 streamReducer / AgentEvent 契约 / 工具入参出参 schema 这些纯逻辑层抽成框架无关的 TS 包**（agent-protocol 已经是这个定位，扩展它），让 Vue 和 React 两端共享逻辑、只各自写 UI，把漂移面压到最小——这是退而求其次时守住"单一真相源"的办法。
- 移动端 SSE 后台策略（前台 SSE+续传+推送补）写进移动端 workbench 设计，与框架解耦。

### 诚实边界

- 我没读 apps/web 现有组件实码，"Capacitor/Expo 复用率≈100%"是据技术方案 §17 桌面 Wails 已做到的推断；`useAgentSession` 是否耦合 Next.js/浏览器 API、套壳要改几处，**以实码为准**，这是复用路线能否成立的判官。
- "vue3 native"我按"vue 系原生 app 方案"理解；若你指特定框架（某个 vue-native 库/方案），其渲染模型/生态可能改变对比结论，请校准这个词。
- 小程序权重、能否接受 WebView 壳，是产品/体验决策，我不知道，标开放问题——选型最终卡在这两问，不在框架本身。
- 原型是静态 mock 演示形态，**真 app 的后台 SSE 断流/推送/原生手势/键盘弹起/离线**这些原型体现不了，只在分析里讲；原型里的"流式"是 JS 定时器模拟，不是真 EventSource。
